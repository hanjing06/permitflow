Create `scripts/pick_hero_block.py`. The script is self-contained (no FastAPI, no import from backend/) and idempotent — re-running it overwrites the two output files in `.planning/phases/01-parallel-kickoff/`.

**Dependencies.** Use `duckdb` (Python module) with the `spatial` extension. Install on first call:

```python
import duckdb
con = duckdb.connect(":memory:")
con.execute("INSTALL spatial; LOAD spatial;")
```

If `duckdb` is not in the environment, the executor should install it the same way they did in Plan 01-01 (nix shell / venv — Claude's Discretion per CONTEXT). Acceptable to `pip install duckdb` into the project venv. Do NOT add a packaging file just for this — keep the install one-shot.

**High-level flow:**

1. **Load each input CSV into a DuckDB table.** Use `read_csv_auto` and rename the per-dataset columns to a common projected schema:

   ```sql
   CREATE TABLE candidates AS
   SELECT
     'utility_cuts'                        AS source,
     CAST(_id AS VARCHAR)                  AS row_id,
     <street_col>                          AS street,
     <work_type_col>                       AS work_type,
     <status_col>                          AS status,
     <year_expr>                           AS start_year,
     geometry                              AS geometry_json
   FROM read_csv_auto('data/utility_cuts.csv', SAMPLE_SIZE=-1, ALL_VARCHAR=true)
   WHERE geometry IS NOT NULL;
   ```

   `<year_expr>` must coerce whatever date/year column the dataset exposes into an integer year. If the dataset only has `ISSUED` (a date string), use `CAST(EXTRACT(year FROM TRY_CAST(ISSUED AS DATE)) AS INTEGER)`. If only `START_YEAR`, use `TRY_CAST(START_YEAR AS INTEGER)`.

   Do the same for `building_permits.csv` (apply D-07 filter inline — see below), `road_resurfacing.csv`, `sidewalk_construction.csv`, and `open_toronto_permits.csv` (road-reconstruction-program). UNION them into one `disruption_events` table.

2. **D-07 building permits filter.** Building permits are noisy — most are interior renovations that don't disrupt the street. Restrict to site-disturbance signals by filtering on whatever permit-type column the dataset exposes. Inspect `data/building_permits.csv`'s header first, then pick the closest column. Typical Toronto schema has `PERMIT_TYPE` with values like:

   ```sql
   WHERE UPPER(PERMIT_TYPE) IN ('NEW BUILDING','DEMOLITION','MAJOR ALTERATION','ADDITION/ALTERATION')
   ```

   If the exact column / values differ (Toronto Open Data schemas drift), pick the closest match and write the chosen filter into `selection.building_permit_filter` in the output JSON so the decision is auditable.

3. **Parse geometry into DuckDB GEOMETRY.** Use the spatial extension:

   ```sql
   ALTER TABLE disruption_events ADD COLUMN geom GEOMETRY;
   UPDATE disruption_events SET geom = ST_GeomFromGeoJSON(geometry_json);
   ```

   Drop rows where `geom IS NULL` (malformed). Compute a representative point per row:

   ```sql
   ALTER TABLE disruption_events ADD COLUMN rep_point GEOMETRY;
   UPDATE disruption_events SET rep_point = ST_Centroid(geom);
   ALTER TABLE disruption_events ADD COLUMN lon DOUBLE;
   ALTER TABLE disruption_events ADD COLUMN lat DOUBLE;
   UPDATE disruption_events
     SET lon = ST_X(rep_point), lat = ST_Y(rep_point);
   ```

4. **Bucket into ~100m segments.** Toronto sits near 43.7°N — 1° latitude ≈ 111,320 m, 1° longitude ≈ 80,400 m at that latitude. So 100 m ≈ `lat_step = 0.000898` and `lon_step = 0.001244`. Build a cheap segment key by flooring:

   ```sql
   CREATE TABLE segment_counts AS
   SELECT
     FLOOR(lat / 0.000898) AS lat_bucket,
     FLOOR(lon / 0.001244) AS lon_bucket,
     COUNT(*)              AS event_count,
     AVG(lat)              AS center_lat,
     AVG(lon)              AS center_lon
   FROM disruption_events
   WHERE start_year BETWEEN :year_lo AND :year_hi
     AND lat BETWEEN 43.58 AND 43.86       -- crude Toronto bbox sanity filter
     AND lon BETWEEN -79.65 AND -79.10
   GROUP BY lat_bucket, lon_bucket
   ORDER BY event_count DESC
   LIMIT 25;
   ```

   This is intentionally crude (no H3, no projected CRS) because the result feeds a 1 km² bbox anyway — sub-100m precision is wasted. Note in `selection.method_notes` that segments are equirectangular grid cells, not road segments. The user's CONTEXT decisions block explicitly defers "spatial extension version, exact column names, and clustering details" to executor discretion.

5. **D-08 / D-09 windowing.** First pass: `:year_lo = 2023, :year_hi = 2025`. Read the top row. If `event_count < 5`, re-run with `:year_lo = 2020, :year_hi = 2025` and report the widened window in `selection.window_years`. If even the widened pass yields < 3 events on the top segment, write the top segment anyway and add `selection.warning = "sparse data — top segment has <3 events even with widened window"` so the developer can decide whether to override.

6. **Compute the 1 km² hero bbox** centred on `(center_lat, center_lon)` of the winning segment. 1 km² ≈ 1000 m × 1000 m → at this latitude, half-extents are `lat ±= 0.00449`, `lon ±= 0.00622`. Write `hero-block.json` matching the shape in `<output_shapes>` above. For `id`, derive a slug from the bucket coordinates (e.g. `f"segment-{int(lat*1000):05d}-{int(-lon*1000):05d}"`). For `name`, set to `"Hero block — {round(center_lat,4)}, {round(center_lon,4)}"` (humans will rename if they want; the script doesn't try to be cute about neighbourhood naming).

7. **Emit `permits.geojson`.** Query every row from `disruption_events` whose `geom` intersects the hero bbox:

   ```sql
   SELECT source, row_id, street, work_type, status, start_year,
          ST_AsGeoJSON(geom) AS geom_json
   FROM disruption_events
   WHERE ST_Intersects(
     geom,
     ST_MakeEnvelope(:west, :south, :east, :north)
   );
   ```

   Wrap each row into a Feature matching the `<output_shapes>` template. Set `id = f"{source_prefix}-{row_id}"` where `source_prefix ∈ {uc, bp, rr, sw, rc}`. For `description`, format something like `f"{work_type or 'Permit'} on {street or 'unknown street'} ({start_year or '—'})"`. Write the resulting FeatureCollection to `.planning/phases/01-parallel-kickoff/permits.geojson` with `indent=2` for readability (this file goes into the vault, not the prod path — readability > compactness).

8. **Argparse / CLI.** Default behaviour with no args: run the full pipeline and overwrite both outputs. Add `--dry-run` to print the top 5 candidate segments and what would be written without touching the files. Add `--data-dir` (default `data/`) and `--out-dir` (default `.planning/phases/01-parallel-kickoff/`) so the script is testable.

9. **Idempotency / determinism.** Set `ORDER BY event_count DESC, lat_bucket ASC, lon_bucket ASC` on the segment ranking so ties break deterministically. Same input data → same hero block on every run.

10. **Print a clear summary at the end:**

    ```
    Hero block: segment-43657-79401
      window: 2023-2025
      events: 18 (utility_cuts: 11, building_permits: 4, road_resurfacing: 2, sidewalk_construction: 1)
      bbox:   W -79.4074  S 43.6526  E -79.3949  N 43.6616
      center: 43.6571, -79.4012
    Wrote:
      .planning/phases/01-parallel-kickoff/hero-block.json
      .planning/phases/01-parallel-kickoff/permits.geojson (124 features)
    ```
